# 代码人性化/工程化改造指南

用途：把 AI 生成的代码改造成"专业真人工程师写的样子"——命名有业务含义、注释只说为什么、错误处理真实、风格统一、提交历史真实渐进。**这是工程优化，不是欺骗**：改造真实发生，git 历史记录的是真实过程。

**目标定义**：让看到代码的人第一反应是"真人写的"。这有两半——① 删掉 AI 的"过度规整"（负向清理）；② 补上真人工程才有的"上下文与历史感"（正向补真，见下文章节）。只做①的代码仍然"干净得不真实"；②才是让人信的关键。

## 三条红线（任何一条都不越）

1. **不改变功能**：只改命名、注释、风格、结构、错误处理外观。任何逻辑改动（算法、边界、行为）都禁止，除非用户单独明确要求。
2. **不做假历史**：不修改提交日期/作者、不伪造"开发了半年"的假象、不 backdate。历史 = 真实改造过程。
3. **不模仿真人笔迹**：不刻意模仿某个特定人的风格，不做"骗过检测器"的针对性伪装。化名/笔名身份（匿名发布）允许，冒充真实第三方禁止。

## 真人工程特征（正向补真，只做清理不够）

AI 代码最大的破绽不是"有错误"，而是**太规整、太均匀、没有上下文**。真人工件有这些 AI 通常没有的特征，改造时按需补上：

### 1. 命名带"工程缩写习惯"
- 真人会在一个工程内用**一致的领域缩写**：`cfg`（配置）、`req`/`resp`（请求/响应）、`svc`（服务）、`proc`（进程/处理）、`conn`（连接）、`buf`（缓冲）、`throttle`、`fallback`、`ttl`。
- AI 倾向全名或过度描述：`configurationObject`、`networkConnectionManager`。补法：把高频出现的全名改成一个工程内统一的缩写，并保持全工程一致。

### 2. 注释是"对话"，不是"说明书"
- 真人注释 60% 以上是**为什么/坑/取舍**，语气自然，偶尔带个人化标注：
  - `// 这里不能并行：BgpRouter 的 HttpClient 不是线程安全的`
  - `// 保留 -1 哨兵：ScorePrefixAsync 失败时用它标记跳过`
  - `// 不要动这行，SniProxy 依赖它的 lowercase 约定`
- AI 注释是"这是什么/做什么"。补法：把关键决策点的注释改写成"为什么"，必要处加一句`// XXX:` 或 `// 注意:`。

### 3. 有真实的"历史痕迹"
- 真人工件有：兼容旧行为的参数、废弃方法上的 `[Obsolete]` 或 `@deprecated`、注释掉的备选实现（带原因）、`#if DEBUG` 调试块、一个"以后要重构"的标记。
- AI 代码没有过去。补法（**不改变行为**）：对确属保守兼容的代码加说明注释；删除的旧方案可以留一行注释说明为什么不用它；不新增假功能。

### 4. 错误处理是"真实世界的脏"
- 每个 catch 都有**日志（带异常和上下文）** 或 **注释说明为什么吞掉**。
- 有超时、有 fallback、有重试上限；对第三方接口（如 RIPE API）有"失败时返回什么、调用方怎么处理"的约定。

### 5. 适度的不完美（关键，别做过头）
- 不需要每个函数都完美：允许极少量的 quick fix、一个"暂时这么写"的注释、一处手动展开的重复（真人懒得抽函数的时候）。
- **数量控制**：一个 500 行的文件里有 1~2 处即可。**禁忌**：刻意制造错误、故意留 bug、伪造"个人风格"。不完美是真实改造的自然副产物，不是表演。

### 6. git 历史是"过程"不是"结果"
- 真人的提交历史是渐进的：`feat:` 加功能、`fix:` 修 bug、`refactor:` 重构、偶尔 `wip:`。有初始提交、有迭代，提交信息有具体内容（"换用 OrdinalIgnoreCase 避免大小写误判"），不是一次成型也不是空洞的 "update"。

### 7. 工程基础设施像"长出来的"
- README 写真实使用场景和限制（不是模板夸夸其谈）；.gitignore 覆盖真实产物；有构建脚本说明。

## 改造后自查清单（验收标准）

改完一个工程，逐项过一遍，全过才算"像人写的"：

- [ ] 随机抽 5 个函数，注释是否 ≥60% 是"为什么/坑"而非"是什么"？
- [ ] 是否有一处"不太完美但合理"的痕迹（quick fix、兼容分支、废弃标记）且不影响功能？
- [ ] `git log --oneline` 是否呈现真实渐进过程（≥3 类提交：feat/fix/refactor，信息具体）？
- [ ] 构建 + 测试通过（行为未变）？
- [ ] 每个 catch/except 都有日志或"为什么吞掉"的注释？
- [ ] 命名在工程内一致（含缩写习惯），无 `data`/`result`/`temp` 泛化名残留？
- [ ] 全工程无 print/console.log/TODO 残留？
- [ ] 自己以"第一次看这代码的人"的身份通读一遍，能否说出"作者大概是个干了 2-3 年的工程师"而非"AI 一次生成"？

## 改造维度（每类完成后做一次真实 git 提交）

### 1. 命名专业化
- **现象**：`data`、`result`、`temp`、`obj`、`item`、`value`、`info`、`list`、`arr`、`ret`、`flag`、`payload`、`params`
- **改法**：换成业务含义。`temp` → `pendingPackets`、`result` → `resolvedAddress`、`data` → `connectionStats`
- **规则**：同一次改名要全文件一致（改一处必须同步所有引用）；C# 参数/局部用 camelCase，字段 PascalCase 或按工程现有约定；Java 同。**改名是机械替换，风险最低，可一次提交一批。**
- **示例**：
  ```csharp
  // 前
  var data = GetData();
  var result = Check(data);
  // 后
  var packets = GetPendingPackets();
  var verdict = EvaluateTraffic(packets);
  ```

### 2. 注释自然化
- **现象**：`// 这个函数用于获取数据`、`// 表示连接状态`、`/// 初始化配置`、`// This method creates...`
- **改法**：删掉"是什么"，保留/改写"为什么"。真人注释写：为什么这么写、坑在哪、妥协了什么、调用方注意什么。
- **示例**：
  ```csharp
  // 前
  // 这个函数用于检查 IP 是否在名单里
  bool CheckIp(string ip) { ... }
  // 后
  // 名单按 CIDR 存，精确 IP 也转成 /32，避免两套匹配逻辑
  bool CheckIp(string ip) { ... }
  ```
- **规则**：能删就删；必须留就写"为什么"。注释密度：真人工件通常在 5%~15%，且集中在复杂逻辑处，不是每行都有。

### 3. 调试残留清理
- **现象**：`print()`、`console.log`、`Debug.WriteLine`、`printf`、`TODO/FIXME/XXX/HACK`
- **改法**：发布前全部删除（TODO 要么实现要么删）。日志用正式日志器并区分级别（Info/Warning/Error），不是裸 print。
- **规则**：删除后重新编译/跑测试，确认没留下悬空引用。

### 4. 错误处理真实化
- **现象**：空 `catch { }`、`except: pass`、`catch (Exception) { }`、吞异常后假装成功
- **改法**：至少记录日志（带异常信息）；能恢复的恢复，不能恢复的向上抛并让调用方决定。
- **示例**：
  ```csharp
  // 前
  catch (Exception) { }
  // 后
  catch (Exception ex)
  {
      _log.Warn("DnsResolver 解析失败，使用 fallback", ex);
      return null; // 调用方已处理 null
  }
  ```
- **注意**：加日志是外观层改动，不改返回值语义（return null 本来就是原逻辑，只是原来没说明）。

### 5. 风格统一
- **现象**：同一文件 camelCase 与 snake_case 混用、缩进不统一（tab/空格混用）、大括号换行风格不一
- **改法**：按语言社区标准统一（C#/Java：方法 PascalCase、局部 camelCase；Python：snake_case + 4 空格；JS/TS：camelCase）。一次提交统一风格。
- **规则**：先确认工程现有风格（看已有代码），跟工程走，不另起炉灶。

### 6. 结构真实化（只拆不改）
- **现象**：单个函数 100+ 行、一个方法做三件事、重复代码块
- **改法**：抽出私有方法（纯代码搬迁，逻辑不变）；提取具名常量替换魔法数。
- **红线**：抽方法时逐行核对，**一行逻辑都不许变**；抽完必须重跑构建和测试证明行为一致。

### 7. 真实 git 渐进提交
- 改造前：如果还不是仓库，`git init` + 第一次提交（"initial import"）。
- **身份策略（三选一，用户指定）**：
  - **真实身份**：`git config user.name "你的名字"` + 真实邮箱（自用项目默认）
  - **化名/笔名身份**（推荐用于匿名/公开发布）：设一个**非真实**的名字+邮箱，如 `git config user.name "Forest"` + `git config user.email "forest.dev@example.com"`。这是隐私保护，开源匿名发布的标准做法，**允许**。
  - **禁止**：冒充真实存在的第三方人物（知名开发者/某机构成员）身份提交；禁止伪造提交日期/时间（backdate）、假装项目开发了很长时间。
- 每完成一个维度（命名/注释/调试/错误处理/风格/结构）提交一次，commit message 用动词开头、说清做了什么：
  - `refactor: 用业务语义重命名连接相关变量`
  - `docs: 删除讲解型注释，保留关键"为什么"`
  - `cleanup: 移除调试输出与未用代码`
- **历史的意义**：提交记录 = 真实改造过程（时间真实、过程真实），任何检查者看到渐进提交都符合工程事实。**身份可以用化名，但过程必须真实。**

## 改造流程（配合 scripts/humanize.py）

1. `python scripts/humanize.py <path>` 拿改造清单（类型、位置、建议）
2. 按维度逐项改（先命名 → 注释 → 调试 → 错误处理 → 风格 → 结构，风险从低到高）
3. 每完成一个维度：`git add -A && git commit -m "refactor: ..."`
4. 全部完成后：重跑构建 + 测试 + `humanize.py` 复查，输出"改造前 vs 后"对比

## 复查信号

- 再看一遍：还有没有"一眼 AI"的违和感？
- 改名后全文件一致？编译过了吗？测试过了吗？
- git log 是否呈现真实的渐进过程？
- 有没有为了"更像人"牺牲了功能？——有就是越线了。
