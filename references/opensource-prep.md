# 开源发布前 AI 痕迹清理

用途：准备把自研代码公开发布（开源/分享）之前，清理掉"一眼 AI"的工程化痕迹，让代码以专业工程的面貌出现。

**立场边界（重要）**：本流程做的是**真实的工程专业化**——删废话注释、改泛化命名、清调试残留、用真实提交管理。**不做**：伪造 git 提交历史冒充长期开发、刻意模仿某真人风格、制造"像人类"的假象对抗检测器。前者让代码更好，后者是欺骗。

## 发布前检查清单

逐项执行，每项都对应 `analyze_repo.py` 的指标：

| # | 检查项 | 怎么做 | 对应指标 |
| --- | --- | --- | --- |
| 1 | 注释清理 | 删"讲解型"注释（解释"是什么"的），只留"为什么"和"坑"；语气统一为工程口吻 | comment_ratio / 抽查注释语气 |
| 2 | 命名规范化 | 泛化标识符（data/item/result/temp/obj/value）改为有业务含义的命名 | generic_identifiers_per_1k_lines |
| 3 | 调试残留清理 | 删尽 print/console.log/Debug.WriteLine/printf；检查 TODO/FIXME 是否已处理 | debug_leftovers |
| 4 | 死代码清理 | 删未使用 import、占位 return（return null/0）、stub 函数、立即重赋值、注释掉的旧代码 | dead_code.* |
| 5 | 工程文档 | 补 README（用途/构建/用法）、LICENSE（选一个开源协议）、CHANGELOG | — |
| 6 | 真实 git 管理 | 从发布起用 git 小步提交（按功能拆分，写清楚 commit message）；**不伪造历史** | git.* |
| 7 | .gitignore | 排除构建产物：bin/、build/、obj/、out/、node_modules/、*.log | — |
| 8 | 文件卫生 | 统一换行（LF/CRLF 按平台）、编码 UTF-8、删除临时文件 | — |

## 执行流程

1. 运行 `scripts/analyze_repo.py <path>` 拿到基线指标
2. 按上面清单逐项清理（命名和注释逐文件过，死代码按脚本候选列表核实后删——**脚本只给候选，删前必须人工确认**）
3. 清理完再跑一次脚本，对比指标：comment_ratio、generic_identifiers、debug_leftovers、dead_code 应显著下降
4. 输出清理报告：清理了什么、改了多少文件、剩余风险项

## 常见遗漏（专门提醒）

- **样例代码/示例数据**：AI 常在代码里留"示例"风格的占位（Example usage、Sample data）——发布前删或改为真实文档
- **日志语气**：AI 的错误消息"礼貌且正式"，真工程会区分 warning/error 级别——按项目实际调整
- **版本号与元数据**：检查 package/版本号/作者字段，别留 `1.0.0` 占位或 AI 默认值
- **硬编码路径**：AI 常写死 `C:\Users\...` 或 `/tmp/...`——改为配置或相对路径
- **依赖锁定**：列出确切依赖版本，别留"pip install xxx"式口语说明

## 复查信号

清理后再自问：如果陌生开发者打开这个仓库，**有没有一眼的违和感**？重点看：README 是否像真人写的、提交历史是否真实渐进、注释是否只说"为什么"、有没有人在用和修这个项目的样子。
